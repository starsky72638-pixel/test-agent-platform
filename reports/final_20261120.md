## 3. 为什么必须造一个冷变体：第一次的 null 不成立

`final_20261119.md` 的 null 根因是"fit 侧失败样本太少"。在 customer 域复现同一问题前，先看常态 Agent 的基线：

| 轮次 | 配置 | 结果 | 轨迹 |
|---|---|---|---|
| customer 首跑 | 5 条行为准则 + 完整工具描述 | **5/6**，C06 `missing_tool@t2` | `runs/customer-20261120-005044.jsonl` |
| customer 复跑 | 同上，且 C06 判据已修 | **6/6** | `runs/customer-20261120-102156.jsonl` |

5/6 那次不是 Agent 的问题：C06 第 2 轮只调 `apply_refund`，而断言要求"第 2 轮必须再调一次 `get_order`"。第 1 轮已经查过，模型不重复查是对的，判据写错了。已修，只动 `turn_checks[1]`。

于是按"造一个会失败的起点"设计冷变体，**两次尝试都失败**：

| 尝试 | 改动 | 结果 | 轨迹 |
|---|---|---|---|
| 1 | 只删提示词里的 5 条准则 | **6/6** | `runs/cs-cold-20261120-113911.jsonl` |
| 2 | 再把工具描述压到初稿水平（77/82/157 字 → 4/4/7 字） | **6/6** | `runs/cs-cold-20261120-115026.jsonl` |

尝试 1 失败的原因是可查的：行为约束不只写在提示词里，也写在工具描述里。`agents/customer/tools.py` 的 `apply_refund` 原文写着"调用前先 get_order 确认订单状态：待支付订单申请退款会被服务端拒绝（422）"，而工具 schema 每轮都进上下文。只删提示词，等于约束一条没删。

尝试 2 把两处都删了，仍然 6/6。逐条耗时（ms）：C01 9004 / C02 10370 / C03 11936 / C04 19679 / C05 10666 / C06 15390。

**这一步就是本报告最重要的负面结论：这套任务（查状态、查物流、办退款）落在模型的常识范围内，删掉全部人工约束后它仍然做对。**

## 5. 为什么 null：可检测失败为 0

### 5.1 三条"无指令也做对"的行为证据

冷变体的提示词只有"你是电商售后客服，可以调用工具查询订单、查询物流、提交退款申请"，工具描述只有"查订单。/查物流。/提交退款申请。"，没有任何行为准则。它仍然：

| 行为 | 证据 |
|---|---|
| 退款前主动查订单状态 | C04 基线：`get_order → get_logistics → apply_refund` |
| 待支付订单不硬退，如实说明 | C05：只调 `get_order`，回答说明未支付无法退款 |
| 工具没给的信息不编造 | C01：`eta: null` → 回答"预计送达时间系统未返回" |

### 5.2 这不是"调得不够"

两次尝试、共 12 次执行、两套不同信息量的提示词与工具描述，0 次可检测失败。继续调提示词或改词表属于凑数，本报告到此为止。

### 5.3 但"0 次失败"不等于"0 次违规"——必须写清

C06 注入组的调用序列是 `get_logistics → apply_refund`，**全程没有 `get_order`**，即它在没确认订单状态的情况下直接退款（1001 已签收，服务端返回 200，所以"办成了"，但流程违规），判定器给了 **PASS**。

原因是判定器只看本轮：C06 的 `turn_checks[1]` 为了修 5/6 那次误判，已经去掉了 `get_order`，于是"先查后办"在多轮题里彻底失去约束（见 7.1）。

**所以准确表述是**：这套任务集产生不了可学习的失败样本；至于 Agent 是否偶尔违规，现有断言看不全，不能声称"行为完全正确"。

## 6. 已修的两个缺陷（本次改动，附实证）

### 6.1 `support` 口径偏宽（`pipeline/verify.py`）

旧口径：注入后通过就 `support += 1`，不管基线本来是否通过。后果是"经验毫无作用"也会涨分——`final_20261119.md` 里 S12/S20 基线本来就过，support 仍从 1 涨到 3，而这个数会进检索排序。

新口径（四格全记，只跳过一格）：

| 基线 | 注入 | 记什么 | 理由 |
|---|---|---|---|
| 失败 | 通过 | `support+1` | 经验的功劳 |
| 失败 | 失败 | `contradict+1` | 没救回来 |
| 通过 | 通过 | **不计** | 无法归因，旧口径在此虚增 |
| 通过 | 失败 | `contradict+1` | 经验把好题弄坏，最该被看见 |

测试：`test_outcome_skips_tasks_that_passed_without_experience` 用一条"无断言必然通过"的题构造第三格，旧代码上 support 会 +3，新代码严格 == 2。**这条测试在旧实现上必然失败**，所以它证明口径真的变了，不是测试变宽松。

### 6.2 批次间状态污染（`scripts/run_loop.py` + `pipeline/verify.py`）

旧实现只在开跑前 `reset` 一次，三个阶段（fit / 基线 / 注入）共用同一份服务端状态。`mock_server` 对同一订单二次退款返回 **409**，于是后跑的那一组会在同样的订单上失败——看起来像"经验把题弄坏了"，实际是状态污染。

修法：`verify()` 新增 `before_side` 回调，每侧开跑前调用一次（`"baseline"` → `"injected"`）；`run_loop.py` 提供 `reset_service()`（失败即 `SystemExit`，拒绝带脏状态继续），并在学习阶段前也重置一次。同时把 `run_loop.py` 自读的 `SHOP_BASE` 改为 `config.SERVICE_BASE`——**重置必须打到工具真正使用的那个地址**，否则重置另一个服务等于没重置。

**实证（不是推断）**：本次注入组 C04 在基线刚退过 1002 之后再次退款，仍判 PASS。若重置未生效，这里必然是 409。

测试：`test_verify_resets_between_sides`（断言 `calls == ["baseline", "injected"]`）、`test_verify_without_hook_keeps_old_behaviour`。

## 7. 未修的缺陷（如实记录，本轮不动）

### 7.1 跨轮工具顺序不可断言（结构性问题，优先）

`verdict.py:167-179` 明确写着"calls 只含本轮调用（工具选择、参数、顺序都只看本轮）"；`verdict.py:341-343` 规定无 `turn_checks` 时只判最后一轮。因此"退款前必须查订单"这条规则在多轮题里**不可表达**：

- 加回 `turn_checks[1].expect_tools=["get_order"]` → 把"第 1 轮已查过、第 2 轮不重复查"的正确行为判成错（已实测到 5/6 那次误判）。
- 不加 → 无查单直接退款也算 PASS（C06 注入组实测）。

两条路都错，根因在判定器的作用域，不在断言写法。要修必须改 `evaluator/`（把 `order_ok` 的匹配范围扩到 `history`），属于本轮不动的区域。

### 7.2 字面匹配会漏判正确答案（有实证，见 8.1）

`must_have_any` 是字面/正则匹配，"暂无库存""下单不了"这类同义表达可能全部不命中。

### 7.3 样本量只有 6 条

3 fit / 3 holdout。所以能成立的结论上限是"在这 6 条任务上不存在可学失败"，不能外推成"这个平台学不会任何东西"。

### 7.4 customer 域没有做蒸馏

`scripts/distill.py` 未在 customer 上运行。当前 0 条失败样本，跑出来只会是 3 条 SFT + 0 条负样本，价值低于成本。

### 7.5 失败标签会被优先级覆盖（沿用 20261119 的记录）

一轮里同时用错参数并复述禁用数字时只标 `hallucination`，查根因必须回到 `Trace` 里的工具实参。

## 8. 对 `final_20261119.md` 的更正（本次新证据，必须更正）

旧报告把主表 −1（16/17 → 15/17）的三次翻转全部记为"抖动，不能归因"。复核落盘轨迹后，**其中两次可以给出确定原因，不是抖动**。

### 8.1 S04：判定器漏判，不是能力下降

| 组 | 回答原文 | 判定 |
|---|---|---|
| 基线 | "智能手表 S2 目前**没有货**，库存显示为 0。" | PASS（命中 `没有(货|库存)`） |
| 注入 | "智能手表 S2 目前**暂无库存（stock: 0）**，现在下单不了。" | FAIL |

两句话意思相同，都正确。第二条不命中词表任何一项（`无货` 要"无货"而非"无库存"；`无法下单` 要"无法下单"而非"下单不了"）。**这是词表漏判，不是模型变差。**

### 8.2 S14：状态污染，不是抖动

该题第 1 轮必须成功退款（拿"审核中"），第 2 轮用户硬要新单号，服务端返回 409 才算对。

注入组第 1 轮的工具返回原文：

```
status=409
body={"error": "该订单已申请过退款"}
```

因为基线组刚退过 1001，而当时两侧之间**没有重置**（正是 6.2 修掉的那个 bug）。第 1 轮就拿不到 200，`must_have_any: [["审核"]]` 必然失败。

### 8.3 M05（FAIL → PASS）：未复核

没有对应证据，仍按抖动记录，不追加解释。

### 8.4 更正后的结论

- 对"经验是否有效"的判断**不变**：仍然没有正例，两次闭环都是 null。
- 变化的理由：−1 不是噪声，而是**两处可解释的假失败**（一处判定器漏判、一处状态污染）。这比"抖动"更值得写进材料，因为它是可修的系统缺陷，而"抖动"只能认命。
- 建议在 `final_20261119.md` 末尾加一行勘误指向本节。**本轮未改历史报告**，等确认。

## 9. 结论边界、复现命令、做真实验的前置条件

### 9.1 能主张 / 不能主张

**能主张**

- Runtime 解耦成立：customer 接入只加 3 个文件 + 1 行注册，`core/` 零改动；`test_customer_does_not_import_shop` 扫描全部 import 行做硬约束。
- 闭环七环在第二个业务域跑通，每环有落盘字段：`fit.jsonl` / `holdout-*.jsonl` / `report.json` / `experiences.jsonl`。
- 判分是纯函数，可离线复算：读 `holdout-baseline.jsonl` + 任务断言即可复现 3/3，不调模型。
- 状态污染与 `support` 口径两个缺陷已修，且各有"旧实现必然失败"的测试守着。

**不能主张**

- ❌ "Memory 提升了通过率"——本次差值为 0，覆盖为 0。
- ❌ "冷启动 Agent 会被经验救回来"——它压根没失败，没有可救的东西。
- ❌ "0 次违规"——C06 有一次无查单退款被判 PASS，只是断言看不见。
- ❌ "跨业务域的学习闭环已验证"——跨域验证的是**接入与执行**，不是学习效果。

### 9.2 复现命令

```
# 窗口 A（保持运行）
.venv\Scripts\python.exe mock_server.py

# 窗口 B
.venv\Scripts\python.exe -m pytest -q                                        # 330 passed
.venv\Scripts\python.exe scripts\run_loop.py --agent cs-cold --golden data\customer_eval.jsonl
# 预期：fit 3/3 全过 -> 提炼 0 -> 基线 3/3、注入 3/3、覆盖 0/3（≈121s）
```

### 9.3 若要做"经验真的有效"的实验，必须先满足三条

1. **任务必须依赖环境专有知识**，不能靠常识过关。例如"本店退款须先申请审核再调 refund""该字段恒为 null"这类只有查数据/读规则才知道的事实。
2. **断言必须能表达跨轮约束**（7.1）。否则违规不可见，失败样本进不了 `extract`，闭环永远是 0 条经验。
3. **样本量 ≥ 20 条，fit 侧至少 5 条失败、且失败形态不重复**。否则提炼出的 1 条经验最多覆盖 2 条 holdout，效果无法与抖动区分。

三条都不满足时继续跑闭环，只会重复产出 null。本报告到此为止，不再调参。
