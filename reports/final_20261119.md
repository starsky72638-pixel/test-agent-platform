## 1. 一句话结论

这是一次 **Agent Runtime 的运行证据**，不是一次"Memory 提升正确率"的证明。

- Runtime、Trace、Evaluator、Learning Pipeline 四段链路在本轮 **60 次真实执行**里逐环跑通，每环都有落盘字段。
- Memory 的效果 **未证明**：有效注入覆盖只有 2/17，且这两条基线本来就通过。
- 主表差值 −1 **全部来自注入 0 字的任务**，属抖动，不能写成"经验有害"，更不能写成"经验有效"。

## 4. 为什么测不出来：覆盖是天花板

`report.json` 的 learn 段：

| 字段 | 值 |
|---|---|
| fit 题数 / 判分 | 26 / 26 |
| 通过 | **25** |
| 失败 | **1**（S13，`missing_tool`） |
| 候选经验 / 入库 / 被拒 | 1 / 1 / 0 |

fit 只错 1 条 → 只能提炼 1 条经验 → 这条经验的触发标签只匹配到 holdout 的 2 条题，
且这 2 条本来就通过。所以：

**主表在结构上就不可能体现经验效果。这不是检索算法的问题，是 fit 侧失败样本太少。**
要改，只能让 fit 出现更多种失败形态（例如把已有失败模式的新题放进 fit），
而不是调 `min_score` / `top_k` 把覆盖数字做大——那是凑数。

## 8. 已知缺陷（必须写进答辩材料）

1. **`support` 口径偏宽**：注入后任务通过就 `support += 1`（`memory/store.py:148-151`），
   不要求"基线本来失败"。本次 S12/S20 基线本来就过，support 仍从 1 涨到 3，
   而这个数会进检索排序（`memory/retrieve.py:134`）。正确口径应为"基线失败且注入后通过"。
   **本轮未修**（冻结代码），如实记录。
2. **失败标签会被优先级覆盖**：一轮里同时用错参数并复述禁用数字时，只标 `hallucination`
   （`verdict.py:279-296`）。查根因必须回到 `Trace` 里的工具实参。M07 的 B1 就是这样：
   标签是 `hallucination`，真实形态可能还包含 `wrong_arg`。
3. **抖动是常态**：同一题、`temperature=0` 也会翻。主表三条翻转全在 0 字注入上就是证据。
4. **检索是形态硬门槛 + 字符重合**，同义改写会漏；跨形态（单轮↔多轮）经验不通。
5. **判分是规则不是语义判官**，`must_have` 靠字面/正则。
6. **第二个 Agent 只有单测**：`main_agent` 从未进过 `run_loop`，没有基线数据。
